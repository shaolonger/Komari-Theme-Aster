# Aster 下一版产品评审

评审日期：2026-09-22。代码基线：`986298f`，主题版本 `1.1.7`。

核心判断：Aster 已经拥有较完整的监控、网络分析和资产管理能力。下一阶段最有价值的提升，是把这些能力组织成一条可信、简洁的日常工作路径：发现异常、查看证据、比较影响、跟进处理。

“世界上最棒”需要转化成可验证的产品目标：新用户能够快速上手，老用户每天少花时间巡检，出现问题时不会被错误结论误导。当前最大的提升空间在数据语义、信息优先级、上下文衔接和移动端可读性。

## 评审范围与证据边界

- 阅读首页、实例、对比、工作室、卡片/列表、资产和网络组件，以及风险、流量、对比评分、配置、兼容适配等关键逻辑。
- 重新构建当前代码，在本机运行基于仓库官方 Komari 模拟器的演示环境。使用 8 个模拟节点，检查桌面、390px 手机屏幕、浅色/深色、离线节点、零样本任务、资产面板和工作室。
- 演示用当前时间修正了原规模测试的固定历史时间戳，避免把测试数据陈旧误判为产品缺陷。模拟节点名称、价格和监控值不代表真实服务器。
- 额外注入本地 RPC 503 故障：缓存界面继续保留，折叠快捷栏只出现小警告点；展开后才出现完整的缓存说明。
- 本次 `npm test`：49 个测试文件、334 项测试通过；`npm run build` 通过；资源体积预算检查通过。
- 阅读 Komari 官方主题/API 文档和相关主题公开说明，作为生态定位参考。没有对其他主题进行同条件安装、性能测试或完整交互评测，因此不作“已领先全部主题”的排名。
- 本次没有连接真实 Komari 实例，没有复跑整套浏览器规模门禁，也没有进行真实设备耗电、屏幕阅读器全流程或长期线上观测。文中区分代码事实、模拟环境观察和产品建议。

## 产品定位

建议主要服务“管理多台 VPS、关心线路质量与续费成本的自托管用户”，并兼顾他们的公开展示需求。

| 使用者/场景 | 核心问题 | 应优先呈现 |
| --- | --- | --- |
| 站长日常巡检 | 现在有什么必须关注？ | 异常摘要、数据更新时间、关注节点 |
| 网络排障 | 哪个节点到哪个目标变差？何时开始？ | 同目标对比、时间范围、丢包/延迟证据 |
| VPS 资产管理 | 哪些快到期？下个月要花多少？ | 续费日历、支出、数据完整性 |
| 公开访客 | 服务是否可用？节点分布和线路表现怎样？ | 清晰的站点身份、公开状态、精选指标 |
| 手机临时查看 | 是否需要立即处理？ | 最重要的事项和一条短操作路径 |

这些场景可以共用数据和组件，但不宜始终共用同一套首页优先级。建议提供“巡检”和“展示”两套预设，通过合理默认值解决差异，不急于开发两个独立产品。

可争取的产品承诺是：**5 秒知道该看哪里，30 秒找到判断证据，3 分钟完成首次基础配置。** 这是下一版验收目标，尚非现有实测成绩。

## 已经值得保留的基础

| 能力 | 当前已具备 | 下一步应增强的部分 |
| --- | --- | --- |
| 首页 | 总览、运维事项、搜索、多维筛选、保存视图、三种布局、多级排序 | 异常优先级、筛选上下文、默认密度 |
| 实例详情 | 资料完整度、续费、流量预估、系统资料、负载/Ping 历史、节点切换 | 问题上下文、时间线、相关指标联动 |
| 网络分析 | 多目标 Ping、主页任务矩阵、主任务/聚合策略、批量绑定 | 同目标可比性、异常时段、样本解释 |
| 多指标对比 | 趋势、洞察、矩阵、排行、聚焦分析、Markdown/CSV 导出 | 评分可信度、任务预设、结论证据 |
| 资产 | 年化/月均成本、剩余价值、汇率、排除节点、排序 | 续费决策、统计口径、专用工作区 |
| 工作室 | 五个分区、搜索、真实首页草稿预览、撤销、冲突处理、离开提醒、保存失败保留草稿 | 引导、预设、导入导出、修改历史 |
| 工程基础 | 按路由拆包、共享查询、Worker 分析、离屏渲染优化、官方/fork 能力适配和自动化测试 | 长期兼容、弱设备体验、数据语义测试 |

因此，“增加暗色模式”“增加多选对比”“增加 CSV”“增加设置预览”“增加虚拟化”都不应被当成下一版的新卖点，这些方向已经有基础实现。

## 最应先处理的产品问题

### R1：对比评分把相对繁忙程度解释成风险

**代码事实。** `scoreMetricRisk` 对上下行和连接数使用“当前值 / 所选节点最大值 × 100”。只要存在正值，其中最大的节点就得到 100 分，并进入 critical 区间；负载使用 `load × 25`，没有在这里结合 CPU 核数。综合分是可用指标评分的算术平均。

后果包括：两台节点都很空闲时，稍忙的一台仍可能被标成高风险；增加一台更忙的对比对象后，原节点的风险会变化；多核机器可能因相同负载被过度惩罚；单项严重异常可能被其他低分稀释。

**建议。** 分开“容量压力”“网络质量”“组内相对值”和“证据充分程度”。未配置带宽或连接容量时，显示数值/组内位置，不输出绝对风险判断。负载结合核心数，并说明该指标的适用范围。综合摘要先显示最严重的已确认问题，再显示其他指标，缺失数据不作为健康证据。

模拟对比中，三台节点显示相同的综合分 3，仍分别得到“综合最佳/最差”。建议在差异很小、分数相同或样本不足时显示“差异不明显”或“不足以判断”，保留原始差异供用户查看。

**验收。** 只改变对比集合，不得改变节点的绝对风险；低负载高吞吐不得因组内第一被判危险；严重磁盘压力不能被其他正常指标平均掩盖。

### R2：无数据、估算和实测值尚未形成统一语义

**实际观察。** Ping 详情中没有任何样本的任务显示“延迟 —，丢包 0.00%”；提示里同时显示样本 0。代码在没有记录时回退到 `task.loss`，不足以保证该值属于当前时间范围。

**代码事实。** 首页“今日/本月流量”在完全没有历史基线时回退到当前累计计数。明细在请求出错时有提示，但首页摘要仍叫“今日流量”；成功返回空历史也可能走这一回退。

**建议。** 在展示模型中统一区分：实测、估算、部分覆盖、过期、无样本、未配置、能力不支持、读取失败。每个状态有固定文本、颜色和后续动作。无样本丢包率应显示“— / 无样本”；缺少周期基线时显示“今日流量暂不可计算”，累计流量另列；部分覆盖则明确起止时间。

**验收。** 零样本不显示零丢包；读取失败不显示业务零值；只覆盖三小时的数据不宣称代表全天；图表与导出携带同一份数据质量说明。

### R3：时间和流量周期存在跨页面不一致

**代码事实。** 主题已有全局显示时区；对比页也使用了该时区解析自定义时间。但实例页自定义输入仍明确写“北京时间”，并调用北京时区转换函数。首页自然日/月边界使用浏览器本地 `Date.setHours`，没有接收主题时区。

流量周期计算主要使用起止计数差。遇到计数归零时返回重置后计数；若要把它解释为整个周期用量，应累计历史中的有效增量，并处理重置前已用流量。缺少边界样本时也需要说明精度。

**建议。** 明确区分“显示时区”“统计日历时区”“计费周期”。默认让前两者遵循同一站点设定，展示绝对起止时刻；计费流量单独说明重置日和统计规则。任何估算都不能冒充服务商账单。

**验收。** 同一站点在上海和洛杉矶浏览器打开，选择同一站点统计日应得到同一个区间；实例和对比的自定义范围一致；计数多次重置、跨月、夏令时和历史缺失都有明确行为。

### R4：流量预测需要减少虚假的精确感

**代码事实。** 耗尽时间按“剩余额度 / 当前瞬时上下行速率”计算，并用 7 天、30 天阈值判断压力。

**实际观察。** 模拟实例出现“约 52609 天耗尽”。这说明界面缺少合理的展示上限，也容易让用户把一个条件推算当成可靠预测。

**建议。** 先把现有值改称“按当前速率估算”，离线或过期数据暂停预测，极长时段显示“近期耗尽风险低”。后续基于 24 小时/7 天有效增量估算日均消耗，并结合距离配额重置还有多久。显示依据、数据覆盖和区间，例如“按近 7 天用量推算，预计本周期 820–960 GB”。区间须有真实计算依据。

**验收。** 短时突发流量不会让长期预测反复跳级；历史不足时不输出趋势预测；配额即将重置与长期不重置的节点能得到不同解释。

### R5：已有异常入口，但重要事项仍容易被隐藏

**代码与观察。** 运维事项位于可折叠总览内；默认配置将离线节点后移。模拟 8 节点环境中，离线节点没有出现在大卡片首行。用户可以通过“需处理”或在线总览找到它，但需要主动寻找。事项当前只列前 6 项，点击后进入一般实例详情。

此外，运维风险模型主要覆盖上报、到期、流量额度和 Ping 能力不匹配。CPU/内存/磁盘持续压力，以及实际 Ping 质量问题，没有完整汇入同一事项模型；工作台另有 Ping 和流量预测关注列表，形成多个不同口径。

**建议。** 巡检预设中永久保留一条紧凑的异常摘要；正常时安静，异常时给出节点、原因和持续时间。公开展示预设可以保留离线后移。把资源、网络和资产事项统一归类，资料不完整作为配置建议单列。支持查看全部，按严重程度、持续时间和影响范围排序。

**验收。** 无需展开或滚动即可知道存在离线/严重异常；可以区分“2 台节点、5 项问题”；持续异常去重，短暂尖峰不过度打扰。

### R6：监控站自身的同步问题应成为一级状态

**代码与实际观察。** 连续失败后已有缓存提示，但快捷栏折叠时主要只呈现警告点，完整说明随展开显示。它与外观和布局设置放在同一个控件区域。本地 RPC 503 注入复现了这一行为。

**建议。** 首页固定显示“最近成功更新 / 当前连接状态”，同步失败时明确“数据已过期，正在重连”。区分节点 Agent 离线和浏览器无法连接 Komari；后者不能被解释成所有节点故障。各指标保留最后有效值，但取消实时状态暗示，提供重试和诊断入口。

**验收。** 数据过期提示不依赖展开菜单；恢复后明确刷新时间；初次失败、空节点和全部离线呈现不同页面状态。

### R7：选择、筛选和分析之间的上下文不够连贯

**代码事实。** 首页“指定 VPS”同时承担限定显示范围和选择对比对象两个任务；首页对比入口最多带入前三台。首页大部分临时筛选存于组件状态；实例图表类型/范围也主要是本地状态，而对比页已有较完整 URL 状态。

**建议。** 保留显示筛选，另建明确的“对比篮”，展示实际入选对象，不无声截断。允许在卡片/列表加入对比。把首页视图、筛选、排序、实例指标和绝对区间放进可恢复的导航状态。事件跳转应直接定位相关指标和时间，而不是让用户重新选择。

**验收。** 选 5 台时能清楚知道将比较几台及原因；查看节点再返回，筛选和滚动位置恢复；从异常进入图表不丢失时间窗口。

### R8：移动端需要重新分配信息，而不只是压缩桌面界面

**实际观察。** 390px 首页折叠总览后仍包含总览、搜索、风险筛选、排序、分类开关与两条分类筛选；紧凑节点卡片约从屏幕中部开始。展开工作台后，多张正常状态摘要和空列表继续占用纵向空间。对比页首屏主要被节点、指标、时间和任务范围选择占据。

**代码事实。** 紧凑卡片存在 7.5–9px 的辅助文字。若信息需要被读取，单靠缩小字体不足以解决密度问题。

**建议。** 增加移动巡检卡：节点名、状态、最重要的异常/两个核心指标、一个趋势；详情点击展开。首屏只保留异常摘要、搜索和当前视图；多维筛选进入底部面板，已选条件保持可见。对比先展示所选对象和结论，“修改对比条件”按需展开。

**验收。** 390px 无需缩放就能读懂状态及关键指标；主要操作有效触摸范围建议达到约 44px；展开详情不必触碰几个像素宽的图标；无需横向寻找常用指标。

### R9：工作室成熟，但首次成功配置仍依赖理解许多概念

现有分区、预览、撤销、保存恢复值得保留。进一步提升应放在：首次启动的场景预设、按具体字段搜索并定位、从节点问题直达对应设置、版本化导入导出、发布前变化摘要及可回滚版本。

当前主题清单未声明 `configuration`；打包脚本直接打包该清单。可根据支持的 Komari 版本，为后台配置入口声明 `redirect`，直达现有工作室，减少用户寻找入口的成本。这需要后端能力适配，不能假设所有安装版本都支持。[官方主题配置说明](https://komari-document.pages.dev/dev/theme)

## 建议的下一版核心体验

### 1. 巡检首页：让“应该关注什么”位于最前面

信息顺序建议为：站点身份与更新时间 → 当前异常摘要 → 关注节点/保存视图 → 节点集合 → 按需展开的资产与统计。

站点名可小而明确；更新时间不藏在设置里。正常时显示简短状态，严重异常时提供一行高可见度提示。既有运维事项升级为可点开的证据入口，保留全部节点浏览能力。

至少提供三种确定性的状态：

- 正常：没有待处理的已确认异常，明确当前有效覆盖。
- 异常：列出最重要事项、持续时间、影响对象和查看证据动作。
- 数据过期：明确当前判断基于多久以前的信息，暂停作新的健康结论。

避免每次轮询都把列表重排到用户指针下方。保留当前已有交互期间冻结排序的思路，增加“有新的异常排序可应用”或稳定的异常区域。

### 2. 事件与证据：从“高风险”走到“为什么”

这是最值得发展的标志性功能。一个事件至少包含类型、节点/任务、首次观测、最近观测、持续时间、触发规则、相关指标和数据质量。点击后打开对应范围的图表，保留原始数值和阈值。

第一阶段只做当前可验证异常和近期历史片段。跨浏览器的确认、稍后提醒、备注、维护窗口、恢复历史，需要服务端/插件持久化；前端本地记录必须明确其作用范围。不能把“本浏览器刚看到”称作真实故障开始时间。

节点离线应写“Agent 上报中断/节点离线”，不能自动推导业务 HTTP 服务不可用。CPU 与 Ping 同时异常可以标“同时间发生”，没有更多证据时不能宣称已定位根因。

### 3. 网络质量工作台：围绕真实任务比较

已有主页 Ping 矩阵和任务对比，下一步要增强分析单位：从“每台节点的几条线”发展成“节点 × 同一探测目标 × 相同时段”的比较。

- 提供“查看同一目标”“检查晚高峰”“比较异常前后”三个任务预设。
- 相同目标优先，说明来源节点到目标的观测方向；官方未公开目标地址时尊重该边界，使用任务 ID/名称，不推测线路。
- 增加延迟 P50/P95/P99、加权总丢包、最长连续失败、有效覆盖；后端缺少采样证据时不生成连续失败时长。
- 图表在同一时间轴下对齐，联动游标、框选区间和排行；原始/平滑状态及缺口处理在分享结果中可见。
- “各目标聚合值”可作摘要，但不能据此直接评选不同探测任务集合中“最好的 VPS”。

### 4. 资产工作区：把账面统计变成续费决策

保留快速弹出面板，并为深入操作提供完整页面。主信息建议为：未来 7/30 天到期清单、预计应付金额、每月支出趋势、按厂商/地区/用途构成。

“剩余价值”应明确为按规则折算的剩余服务价值，不能让人理解成可退款金额或二手售价。汇率展示基准币种、来源、时间及过期状态。缺少价格/到期时间的节点单独列出统计缺口。

低利用率提示可以作为续费前检查入口，但低 CPU 并不等于可退订：备份、灾备、低延迟接入都有保留价值。给出“建议复核”及依据，不自动建议停止服务。

### 5. 对比入口：从自由拼装到一键开始

保留专家能力，增加任务预设：“资源压力”“线路稳定性”“异常前后”。先给出默认合理的节点、指标、窗口；复杂设置折叠为“调整条件”。

结果先呈现证据充分的差异；趋势/矩阵/排行为进一步探索。导出沿用当前 Markdown/CSV，加上绝对时间、时区、目标范围、样本覆盖、统计方法与版本，提供可重开的分析链接。分享链接引用实时数据，固定快照则必须明确存储及访问权限。

### 6. 展示预设：兼顾站点个性与访问者任务

加入小型站点标识、简介/公告、精选节点和公开状态摘要。外观预设可采用“清晰巡检”“紧凑终端”“柔和展示”，保留当前背景能力，同时提供足够可读性。

站长视图和访客视图可有不同默认信息。成本、内部用途等字段的展示开关只是视觉策略；需要真正保密的数据必须由服务端限制返回。主题设置经公开 API 下发，不应用来存放通知 Token、私密备注或私密分享凭据。[官方主题数据边界](https://komari-document.pages.dev/dev/theme)

## 视觉与交互细节

| 方面 | 当前倾向 | 建议 |
| --- | --- | --- |
| 色彩 | CPU、内存、磁盘、速率、Ping、到期同时使用较强颜色 | 正常信息降低饱和度，异常使用统一语义；高吞吐仅表示量级时不要复用危险暗示 |
| 层级 | 多个近似权重的面板、边框、标签和小字 | 采用“结论—证据—完整数据”三层，去掉无增量信息的重复摘要 |
| 密度 | 大卡片占高、紧凑卡片字号小 | 舒适/紧凑/专家密度应调整字段数量与展开方式，保持可读字号 |
| 图表 | 专业数据丰富，部分解释依赖悬停 | 手机点击固定提示；缺口、平滑和时间范围直接可见；提供可访问数据摘要 |
| 数值 | 百分比/延迟常带较多小数 | 默认按决策需要展示精度，详情与导出保留精度，避免小数产生虚假确定感 |
| 弹层 | 已有 Escape 和点击外部关闭 | 根据弹层性质补齐焦点进入/返回；真正模态弹层才限制背景交互，统一语义 |
| 空态 | 部分路径提供概括提示 | 区分未添加节点、筛选无结果、权限不足、能力不足、无历史和通信失败，分别给出动作 |
| 动效 | 有趋势、颜色和状态变化 | 只帮助定位变化；在密集卡片和弱设备上提供低动态模式，尊重减少动态设置 |
| 国际化 | 中文主导，局部中英文术语混用 | 中英语言包、站点基准币种、统一时间/单位格式；统一“节点/VPS、上行/上传、丢包”词汇 |

建议先统一状态颜色、字体梯度、间距、按钮和面板组件，再扩展外观预设。成熟感主要来自清晰、一致和恰当留白，不依赖更多效果。

## 后续实现记录

评审以 `986298f` 和 Aster `1.1.7` 为基线。随后已在 `main` 上逐项实现并提交本版核心改进：P0-1 风险评分语义、P0-2 数据质量与周期流量、P0-3 时区和预测说明、P1-1 常驻异常摘要及证据跳转、P1-2 手机巡检体验，以及 P1-3 对比任务预设和可恢复链接。对比工作台提供“资源压力”和“线路稳定性”起点，链接保留所选节点、指标、时间、视图及 Ping 任务；首页已选节点不会被入口静默截断。

P1-4 的首配部分已加入“日常巡检”和“公开展示”两个草稿预设，均可撤销且需显式保存；主题清单也声明了直达工作室的 `redirect`。按 [Komari 主题开发指南](https://komari-document.pages.dev/dev/theme)，该后台入口需要服务端高于 1.2.0；旧版本仍能通过首页入口访问工作室。预设只调整明确展示的首页选项，不替管理员猜测网络绑定、费用或节点资料。

本记录描述源码实现和模拟浏览器门禁，不代表已在真实 Komari 实例或真实用户群中验证。其余同目标网络诊断、续费工作区、事件持久化和国际化留待后续版本。

后续版本先做同目标网络分析和续费工作区，逐步建立特色；再拓展跨设备事件流程、国际化和模板生态。版本号可按实际发布范围决定，无需为愿景直接重写成 2.0。

## 实现边界

可同时安排的低成本改进：将“资产”明确为“剩余服务价值”或以月均支出作为入口；将“在线时长”与“系统运行时长”分开命名；给首页增加小型站点身份；统一 README 的版本演进说明与实际 1.1.x 发布序列；随发布更新预览图。当前根目录预览图仍包含与本次实际页面不同的摘要项和“3D”入口，容易让新用户对安装结果产生错误预期。

| 主题可先完成 | 需要后端/插件配合或验证 |
| --- | --- |
| 状态文案、评分展示、同窗口图表、移动布局 | 长期事件记录、确认/维护状态跨设备同步 |
| 保存当前筛选、对比 URL、可访问弹层 | 可靠定时通知、Webhook 投递与密钥存储 |
| 基于已公开数据做统计并标注覆盖 | 真实业务可用率、日志/部署关联、精确历史容量 |
| 配置文件导出与导入前差异预览 | 历史配置中心、并发版本控制 |
| 公开页面的呈现开关 | 服务端字段权限、私密分享、受保护快照 |

现有仓库已经记录过全局 Telegram 报告等后端工作，不能简单当作从零缺失。下一步应确认目标 Komari 后端/分支实际可用能力，接入已有通知或报告入口；不要仅用浏览器定时器实现离线通知。官方 `/admin` 和 `/terminal` 由系统界面负责，主题适合提供上下文链接并延续相关节点信息。[官方主题开发指南](https://komari-document.pages.dev/dev/theme)

## 性能与持续质量

本次首页资源预算实测：JS Brotli `160,739` 字节，CSS Brotli `22,060` 字节，字体 `48,256` 字节，现有预算检查通过。首页 JS 已接近仓库的 160 KiB 上限，新增事件、网络分析和资产页面应继续按路由加载。

代码已有 30/300/1000 节点的双后端浏览器规模场景，以及离屏内容/绘图检查。本次仅阅读了这些门禁，不把它们记作本次运行成绩。

一个值得专项测量的路径是：首页为了流量总览，定期为可见节点查询最长 31 天历史。应比较“首页小摘要按需取数”和“打开月统计才请求月历史”的请求体积、解析时间与首屏体验；不要在未经测量前直接认定它导致卡顿。

建议发布验收增加以下产品场景：

- 正常高吞吐、单节点离线、全局 API 失败、零样本 Ping、部分历史和计数重置。
- 3/30/300/1000 节点，0/1/多探测任务，长名称、多语言、缺价格和缺分组。
- 390px 手机、桌面、200% 缩放、键盘操作、浅/深色、复杂背景和减少动态模式。
- 首页筛选 → 实例 → 对比 → 返回；分享区间；保存中继续编辑；配置冲突与失败重试。
- 慢网络、后台标签页再激活、连续运行、真实手机电量消耗；这些需独立测量，不能由本机打包体积替代。

建议招募 8–12 位代表用户，包含新用户、5–20 台 VPS 站长和较大节点规模用户，完成相同任务。记录首次发现异常时间、理解状态的错误率、找到证据时间、首次设置完成率及移动误触。先测当前版基线，再与候选版比较。

关键准入条件：零样本与离线不得被误认为健康；严重异常在首屏可见；选定对象和时间不丢失；新版本不要求老用户重做既有配置。使用数据采集应由用户自愿参加，也可以通过人工可用性测试完成验证。

## 生态参考与差异化

- [Mochi](https://github.com/svnmoe/komari-web-mochi) 公开说明包含六种节点/任务视图及 Earth 视图。其仓库当前已归档，适合作为交互参考，不作为持续维护状态的正面保证。
- [PurCarte](https://github.com/Montia37/komari-theme-purcarte) 明确采用磨砂玻璃视觉方向，说明个性化外观已经是生态中成熟的一类竞争点。
- [Lumina](https://github.com/stqfdyr/komari-theme-Lumina) 的公开说明强调卡片信息密度与流畅度，与 Aster 的历史设计基础相关。
- [官方主题市场](https://github.com/komari-monitor/theme-market) 提供安装目录与校验元数据。高质量演示、清晰兼容矩阵、完整中英说明和一致的版本截图，会直接影响用户是否愿意安装、能否顺利启用。

由此推断，Aster 最值得长期积累的优势是：**可信的判断、清楚的网络证据、实用的资产决策，以及日常使用中的省心。** 视觉风格可以强化识别，但完整的工作路径更难被简单换色或新增一个视图替代。
