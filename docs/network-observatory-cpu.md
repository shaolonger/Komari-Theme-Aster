# 网络观测与 Komari CPU 排查

## 插件 1.14.0：每小时尖峰的进一步修复

本次按反馈的 **52 台 VPS、5 个方案** 审核：国际检测覆盖约 40 台、IPv4 / IPv6 大陆线路各约 15 台，均每小时一次；IPv4 / IPv6 测速分别覆盖约 30 / 20 台，每天 21:00 / 22:00 执行。面板也安装探测器，但未启用自动更新。因此，自动升级器不是这次小时峰值的主要嫌疑。

定位到三种会叠加的工作量：

1. 1.13.0 的 `reportMaintenanceAt` 每小时在调度锁内遍历全部 VPS、各模块的日索引，再逐个解析全局七天结果回执。即使没有任何数据过期，也完整读取历史；上次 1.11.1 修复只把回执扫描从“每个 VPS 一遍”减为“全局一遍”，未去掉这一遍。
2. 同时到期的计划同步为所有 VPS 派发任务。每个缺测目标逐条重写 manifest、日索引和主页投影；读取未完成轮次时反复探测其他尚未完成槽位，使大轮次出现平方级放大。逐条超时 / 共享任务收尾也反复扫描整个队列。
3. 活跃任务的每次领取与回传都完整序列化 `native-state.json`。按上述配置的 750 个目标模拟，750 次领取与回传产生 1,500 次整份快照写入，累计约 421 MB（UTF-8 实际文件字节）；空闲轮询优化不会降低这条路径的开销。

这些路径在官方 Komari 1.4.3 / 1.5.1 的 Goja 内运行，CPU 会计入 `komari` 进程。源码及隔离复现可以解释周期负载，但没有直接登录生产主机采样，不能凭曲线排除其他进程或实际测速消耗。

本版处理：

- 保留期维护使用持久游标、到期索引和按日分桶回执；每片最多 32 步、8 ms 软预算，片间至少 500 ms。稳态跳过未到期历史 JSON。删除按文件推进，保留 7 天明细 / 90 天汇总、活动轮次及回执所有者验证。
- 到期计划只先保存待派发成员和原计划时间，再按每片最多 2 台、8 ms 软预算分发。稳定轮次 ID 防止游标重放重复检测；满队列、过期旧租约尚待清理时保留成员稍后重试。停用 / 删除方案会移除尚未派发的成员。
- 活跃队列按任务 UUID 分成 64 桶，元数据保留在小型 `native-state.json`，实际任务存于 `native-queue/<epoch>/`。正常领取和结果仅提交改变的任务桶，不再序列化全部任务或公共测量目录。单个原子写前事务先保存意图，再应用各桶及必要元数据；进程中断、跨桶部分写入、元数据写失败会在下一次读取前幂等续完，未知版本、损坏或缺失已提交分片会停止写入。
- 同步批次合并每轮 manifest、日索引及主页投影的提交；原始测量和结果回执仍写在摘要之前。单槽查询不再读取上一轮全部 MTR；未完成槽的崩溃恢复只在冷读时进行，脏轮次不会因缓存淘汰丢状态。已完成任务从未完成轮次的 `_jobs` 中移除，原始报告保留；租约进度不再重写内容相同的日摘要。轮次缓存同时受 128 轮和 4,096 槽位约束，让 52 节点交错回传保持命中，并限制大轮次的内存占用。
- 空闲分钟调度与相同维护回报不重复写盘；批量收尾共享一次队列索引和压缩。超时回收分片执行，领取前再次检查有效期，续租会重新验证。
- 路线历史恢复改为按单个测量分片读取，完成标记保存到节点快照；临时 I/O 错误保留原槽位并退避重试。主页摘要按节点缓存，最迟一分钟刷新，并在 24 小时 / 7 天边界即时失效。公开脱敏使用副本，不污染管理员证据。

### 可复现的保留期基准

本机实盘 Node 基准：52 节点、90 天、155,700 轮、9,000 日索引、100,000 回执。旧版一次无过期数据的巡检读取 **109,000 个 JSON / 56.47 MiB**，约 **6.74 秒墙钟 / 2.94 秒进程 CPU**；迁移后的完整巡检约 **39 ms 墙钟 / 24 ms CPU**，这些历史 JSON 读取为 **0**。该比例只适用于这个隔离工作负载。

首次迁移需要逐项建立到期索引、迁移旧回执，总工作量约 **22.1 秒墙钟 / 13.1 秒 CPU**，按生产 500 ms 间隔分成约 3,906 片，至少铺开约 **32.5 分钟**。首次列举十万个旧文件时，单片曾达 **292 ms**：原生目录列举、单个文件读取和 JSON 解析不能被 JavaScript 时间预算中途抢占，因此 **8 ms 是软预算，并非硬上限**。不要因为迁移尚未完成就删除插件数据或重置凭证。

队列专项基准另计量全部事务意图、任务桶和元数据写入，不能将它与完整测量 / 报告流水线混淆。750 次真实领取与回传的专项测试使用合成测量并隔离报告 I/O；未变化的公共测量目录若被序列化，测试会直接失败。完整官方运行环境回归仍覆盖真实轮次入库和恢复。

### 包含真实报告入库的完整流水线

另用同一离线场景比较旧提交 `366ee48` 和本版：52 台清单、70 个真实轮次、750 次成功领取 / 回传，包含 480 份十样本延迟结果、270 份十二跳路由结果、750 个持久回执和 90 个三网投影格。保留真实 `complete / progress / batch`、manifest、日索引及投影 I/O，任务按 VPS 交错；不执行任何外部网络探测。计量以文件实际 UTF-8 字节为准，包含事务日志和所有分片，并且给读写各增加一次统计 `stat`。

本机官方 Goja 1.4.3、单 Go 处理器的完整流水线中：

| 指标 | 1.13.0 | 本版 |
| --- | --- | --- |
| 进程 CPU（用户态 + 系统态） | 10.89 秒 | 5.92 秒 |
| 全部逻辑写入 | 456.8 MB | 37.3 MB |
| 队列 / 元数据写入 | 421.4 MB | 7.7 MB |
| manifest 读取 | 31.6 MB | 0 |
| 日索引写入次数 | 1,500 | 750 |

这个合成完整负载的 CPU 下降约 **46%**，逻辑写入下降约 **92%**。原子事务的小写入次数增加（6,340 → 7,230），用以保留跨文件一致性；它没有消除真实网络测量或磁盘系统的成本。此结果不包含另外测量的小时巡检，也不包含实际外网测量耗时，不能套用为生产整机 CPU 降幅。

复现脚本和分类输出说明：

```sh
go -C scripts/plugin-runtime run ./benchmark-active-pipeline \
  --plugin ../../network-observatory/plugin \
  --scenario ../../network-observatory/plugin/tests/benchmark-active-pipeline.js \
```

以上命令在仓库根目录运行。旧版对照使用单独目录提取的 `366ee48` 插件，`--scenario` 仍指向同一份新场景。脚本拒绝所有 HTTP transport 请求并检查源码前后指纹；详见[完整基准说明](https://github.com/shaolonger/Komari-Theme-Aster/tree/v1.17.0/scripts/plugin-runtime/benchmark-active-pipeline)。

官方 Goja 另有 CI 子集：同样的 52 节点计划分布、14 天共 24,220 轮、4,096 回执。断言冷迁移每个历史索引 / 回执仅解析一次，稳态二者零解析；同时覆盖跨重启删除、写失败恢复、250 槽批次和共享任务。完整脚本：

### 探测器 1.11.0

探测器的改进与面板小时清理是两条不同路径：

- 泰尔测速不再每 32 KiB 执行 TCP_INFO / 字典更新，改为约 250 ms 采样，在预热边界和关闭连接前刷新；上传仍以最终 TCP 已确认字节计量，不能把未确认发送当作成功速率。
- 传输块、HTTP 分帧缓冲复用；iperf3 认证能力按可执行文件身份缓存，工具变更时失效。
- 持久结果队列每次最多扫描 64 项、交付 16 项，失败项不会堵住后续结果，不全目录排序。原始 JSON 仍是重启后的事实来源。
- OpenRC 的可选自动更新检查分钟首次生成并保存，同机全部身份共用；无 `od` 时回退到第 17 分钟。现有正在运行的维护服务重启后才应用新分钟。检测方案的时刻、时区保持原值。

Linux 1 CPU / 128 MiB、独立回环 HTTP 服务、64 MiB 下载的 AB/BA 测试中，客户端 CPU 中位数 **16.844 → 7.591 ms**，TCP_INFO **2,136 → 1 次**。这约 55% 的收益是该客户端下载测试的结果，不能当作生产 Komari CPU 降幅。10,000 条结果的目录枚举 **18.189 → 0.059 ms**，访问条目 **10,000 → 16**。

使用旧提交 `366ee48` 的 runner 目录作为 baseline；只连接本机回环，无公网测速：

```sh
python3 network-observatory/runner/tests/benchmark_performance.py \
  --baseline /path/to/old/runner --candidate network-observatory/runner \
  --iterations 14 --warmup 2 --payload-mib 64 --outbox-records 10000
```

### 更新与核验

优先更新面板插件至 **1.14.0**，主题至 **1.17.0**。旧探测器仍能通信，凭证、计划、报告和公开范围保留；小时清理及调度优化不要求重装 VPS 探测器。探测器 **1.11.0** 的本机传输 / 重试优化可通过现有保留凭证升级命令应用，或由已明确开启的自动更新应用；不要为了升级点击重置凭证。

这是面板插件的存储格式升级。备份和恢复应包含整个插件存储目录，不能只复制 `native-state.json`（其中 `jobs: []` 是分片格式的元数据，并不表示没有排队任务）。若需要回退到 1.13.0 及更早插件，应停用插件并恢复与旧版本匹配的完整存储快照，不能只覆盖旧 ZIP。探测器自身的事务升级 / 自动回滚机制不受此处影响。

恢复测试覆盖进程中断和注入的 I/O 错误；与原有存储接口一样，写入依赖宿主文件系统。它不是物理掉电情况下的零丢失承诺。

迁移时长取决于旧数据规模。完成后用相同检测计划观察至少 2–3 个小时周期，并覆盖一次夜间测速。实际满速测速仍可能使用 CPU 和带宽，不能承诺所有情况下均不出现短暂满核。

管理员登录后可以在浏览器控制台读取内存中的分片统计，无需开启新轮询：

```js
fetch('/api/aster-network-observatory/v3/performance', { credentials: 'same-origin' })
  .then(response => response.json()).then(console.log);
```

包含待派发成员数、队列长度、维护步数、片段最近 / 最大墙钟耗时、超过 50 ms 的次数及下次维护时间。统计在插件重启后重新计数，不写入历史数据库。单片超过 250 ms 的日志限频为至多每分钟一条。若迁移结束后仍有长时间 100%，对齐进程采样、计划时间和该统计继续定位。

## 先确认负载来自哪个进程

在 Komari 面板所在的 VPS 上运行 `htop`。`komari` 是面板服务；`python3`、`mtr`、`nexttrace` 等属于探测器 / 测量工具。同名、相同内存数字的多行可能是线程，在 htop 中按 `H` 切换用户线程显示。`VIRT` 是虚拟地址空间，实际常驻内存看 `RES`，不能把线程行的内存相加。

先关闭 Aster 页面观察，再在 Komari 插件管理中临时停用「Aster 网络观测」观察 1–2 分钟。停用会暂停调度和探测器请求，保留数据及凭证。如果 CPU 明显下降，可以将负载范围收窄到网络观测路径；若仍然高，继续检查 Komari 的其他插件、Agent 上报频率、节点 / 访客数量、历史清理与磁盘负载。单凭进程名称无法判定具体函数。

若 PID 为 `607560`，且系统安装了 sysstat，可采样：

```sh
pidstat -p 607560 -t 1 20
pidstat -p 607560 -d 1 20
```

未安装 pidstat 时用 `top -H -p 607560` 查看线程负载，记录出现时间及持续时长即可。PID 应替换为当前 Komari 进程；Docker 部署时同时参考 `docker stats --no-stream`，区分宿主机和容器中的 PID。

提供问题信息时记录：Komari / 插件版本、面板机器 CPU 核数、节点及大陆测量点数量、同时启用的方案与检测频率、页面是否打开、停用插件前后 CPU 是否变化。日志可以提供同一时间窗口中的错误，勿发送凭证配置、Bearer token 或完整安装命令中的密钥。

## 插件 1.11.1 的修复

旧实现每次探测器轮询和心跳都解析整个 `native-state.json`，空闲轮询也完整写回。探测器空闲每 15 秒轮询一次，有未完成的并发延迟任务时可能每 0.5 秒轮询一次；每个测量端原先还会反复遍历其他节点的任务。这些 JavaScript 在 Komari 的 Goja 解释器内运行，因此 CPU 显示在 Komari 进程中。

本次修复：

- 缓存解析后的状态和凭证，检查文件变动；读取损坏文件和写入失败时清除缓存，凭证重置 / 撤销立即生效。
- 空闲轮询不写队列；建立按测量端划分的任务索引，队列或任务阶段改变时更新。
- 心跳立即更新内存中的在线状态和续租；写盘合并到约 30 秒一次，每分钟调度以及任何任务 / 配置提交也会刷新。进程异常退出时，最近未刷盘的心跳可能回退；任务领取、完成、取消、维护租约与凭证变更仍立即持久化。
- 两个管理目录的频繁刷新，在一分钟内复用一次调度 / 节点清单刷新；每分钟计划调度不变。
- 报告摘要跳过已提交的测量明细，保留未完成提交的崩溃恢复。活动索引及未发生保留期变化的历史索引不再反复重写。
- 全局结果回执每小时扫描一次，不再为每个节点重复扫描全部回执；共享任务匹配仅比较同一 VPS 的任务。

本地官方 Komari 1.4.3 Goja 测试：50 个测量端、7,500 个待测目标，100 次轮询 / 心跳由约 **9,629 ms** 降至约 **83 ms**；整份状态文件读取由 100 次降至 1 次，写入由 100 次降至 0 次。1.5.1 同样通过。场景使用等待中的队列，不包含真实网络测量、报告入库和生产环境 HTTP 并发，不能把耗时比例直接当作实际 VPS CPU 降幅。

运行 `npm run test:plugin-runtime` 可复现修复后的官方运行时检查，包含 2 秒预算及读写次数门限。
