# 网络观测与 Komari CPU 排查

## 先确认负载来自哪个进程

在 Komari 面板所在的 VPS 上运行 `htop`。`komari` 是面板服务；`python3`、`mtr`、`nexttrace` 等属于探测器 / 测量工具。同名、相同内存数字的多行可能是线程，在 htop 中按 `H` 切换用户线程显示。`VIRT` 是虚拟地址空间，实际常驻内存看 `RES`，不能把线程行的内存相加。

先关闭 Aster 页面观察，再在 Komari 插件管理中临时停用「Aster 网络观测」观察 1–2 分钟。停用会暂停调度和探测器请求，保留数据及凭证。如果 CPU 明显下降，可以将负载范围收窄到网络观测路径；若仍然高，继续检查 Komari 的其他插件、Agent 上报频率、节点 / 访客数量、历史清理与磁盘负载。单凭进程名称无法判定具体函数。

若 PID 为 `607560`，且系统安装了 sysstat，可采样：

```sh
pidstat -p 607560 -t 1 20
pidstat -p 607560 -d 1 20
```

未安装 pidstat 时用 `top -H -p 607560` 查看线程负载，记录出现时间及持续时长即可。PID 应替换为当前 Komari 进程；Docker 部署时同时参考 `docker stats --no-stream`，区分宿主机和容器中的 PID。

提供问题信息时记录：Komari / 插件版本、面板机器 CPU 核数、节点及大陆测量点数量、同时启用的方案与检测频率、页面是否打开、停用插件前后 CPU 是否变化。日志可以提供同一时间窗口中的错误，勿发送凭证配置、Bearer token 或完整安装命令中的密钥。

## 插件 1.11.1 的修复

旧实现每次探测器轮询和心跳都解析整个 `native-state.json`，空闲轮询也完整写回。探测器空闲每 15 秒轮询一次，有未完成的并发延迟任务时可能每 0.5 秒轮询一次；每个测量端原先还会反复遍历其他节点的任务。这些 JavaScript 在 Komari 的 Goja 解释器内运行，因此 CPU 显示在 Komari 进程中。

本次修复：

- 缓存解析后的状态和凭证，检查文件变动；读取损坏文件和写入失败时清除缓存，凭证重置 / 撤销立即生效。
- 空闲轮询不写队列；建立按测量端划分的任务索引，队列或任务阶段改变时更新。
- 心跳立即更新内存中的在线状态和续租；写盘合并到约 30 秒一次，每分钟调度以及任何任务 / 配置提交也会刷新。进程异常退出时，最近未刷盘的心跳可能回退；任务领取、完成、取消、维护租约与凭证变更仍立即持久化。
- 两个管理目录的频繁刷新，在一分钟内复用一次调度 / 节点清单刷新；每分钟计划调度不变。
- 报告摘要跳过已提交的测量明细，保留未完成提交的崩溃恢复。活动索引及未发生保留期变化的历史索引不再反复重写。
- 全局结果回执每小时扫描一次，不再为每个节点重复扫描全部回执；共享任务匹配仅比较同一 VPS 的任务。

本地官方 Komari 1.4.3 Goja 测试：50 个测量端、7,500 个待测目标，100 次轮询 / 心跳由约 **9,629 ms** 降至约 **83 ms**；整份状态文件读取由 100 次降至 1 次，写入由 100 次降至 0 次。1.5.1 同样通过。场景使用等待中的队列，不包含真实网络测量、报告入库和生产环境 HTTP 并发，不能把耗时比例直接当作实际 VPS CPU 降幅。

运行 `npm run test:plugin-runtime` 可复现修复后的官方运行时检查，包含 2 秒预算及读写次数门限。

## 更新及复查

在面板覆盖上传 `Aster-Network-Observatory-v1.11.1.zip` 并重新启用插件。保留原插件数据，不需要重新安装各 VPS 探测器，也不需要生成 / 重置凭证。主题 1.14.1 包含相应说明，探测器仍为 1.10.0。

更新后使用相同方案、频率和页面访问方式观察至少一轮检测，并对照停用插件的基线。若仍持续接近 100%，保留上述采样和对应时间的 Komari 日志，继续针对剩余负载定位。
