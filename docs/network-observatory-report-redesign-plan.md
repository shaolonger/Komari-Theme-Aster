# Aster 网络报告重构方案

状态：本文件保留设计基线与测量口径。六阶段的软件实现纳入主题 1.8.0 / 插件与 runner 1.7.0；实际验证及资源边界见[实施记录](network-report-implementation-status.md)，操作见[新版指南](network-report-v3-guide.md)。核对日期：2026-10-01。

代码基线：主题 v1.7.0、网络观测插件 v1.6.0、runner v1.6.0。下文“当前实现”和“待实现”均描述此设计基线；新版交付状态以实施记录为准。
参考对象：[PickMyVPS 的 Lightlayer HKG.PRE 详情](https://www.pickmyvps.com/app/m/lightlayer-hkg-pre?detail=intl)，以及用户提供的七张截图。本次已通过浏览器查看该节点的「路由」「测速」「国际」标签，核对页面实际功能；没有取得其私有后端、探测器源码或第三方接入授权。

## 1. 结论与目标

可以在当前仓库实现这类报告。推荐继续使用 **Aster 主题 + Komari 插件 + 独立测量 worker**，升级报告模型、采集器和调度，不要求修改 Komari/komari-agent，也不要求开启 Web SSH。兼容目标仍为 Komari ≥1.4.3，具体新接口须在官方 1.4.3 插件运行时验收。

此前把产品重心放在「配置独立检测任务、看单条报告」，与用户要的「每台 VPS 的成组网络报告」存在差距。下一步需要围绕 **目标矩阵、检测轮次、原始样本和完整报告** 重构，不能仅靠扩充目标目录或更换卡片样式完成。

目标体验：在实例详情中打开「网络报告」，直接切换 **路由 / 测速 / 国际**，选择最近一轮或历史轮次，查看同一轮中所有目标的结果；管理员一次选择预设、时间和 VPS/分组即可建立计划。测量资源由管理员集中维护，普通计划不再要求逐个填写主机。

软件与公共数据可以采用免费工具和接口；稳定的固定大陆三网、双向不限速测量需要实际可用且允许该用途的端点。这些端点可以是公共服务、合作资源或自有设备，并非必须让用户自建九台探针；但软件不能保证公共资源永久覆盖全部地区和运营商。PickMyVPS [首页说明](https://www.pickmyvps.com/)中的「公开报告免费查看」也不等于开放其测量网络供任意 VPS 调用。

## 2. 七张截图具体要求了什么

| 截图 | 页面内容 | Aster 必须实现的数据与交互 |
| --- | --- | --- |
| 1 · 回程路由 | 地点、三网、TCP/ICMP、逐跳/按 AS 折叠；MTR 表格 | VPS→大陆，保存每跳 IP、ASN、网络、发送/响应数、Last/Avg/Best/Worst、协议、端口、时间；支持同一轮切换地区和运营商 |
| 1 · 去程路由 | 按运营商列出不同大陆城市；完整 MTR 表格 | 大陆→VPS，保存实际测量点身份和接入信息；显示真正从大陆发起的逐跳测量，不能从回程推算 |
| 1 · BGP | 全球 AS 路径图、观测来源、采集器/对等点数、上游变动、RPKI | 针对 VPS 公网 IP 所属的实际路由前缀采集 BGP AS_PATH；单独保存快照、来源和变化 |
| 2–3 · 大陆测速 | 北京/上海/广东三网，共九行；回程/去程；每秒曲线和历史轮次 | 单 TCP 连接双向吞吐；平均/最大 Mbps、TCP RTT、发送端重传、实际字节数；逐秒样本可回放 |
| 4–7 · 国际延迟 | AWS / 网站 / CDN / Telegram；每个目标十个色块 | 每轮每目标十次独立样本，保存实际 IP、协议、耗时和失败原因；统一分组目录、历史轮次与颜色说明 |
| 4–7 · IDC 延迟 | 商家切换，按机房显示十次样本 | 官方或明确公开用于测试的 IDC 端点目录，按商家/机房筛选；独立轮次和覆盖情况 |
| 4–7 · 国际测速 | 十个国际地区；上行/下行；逐秒速率和 TCP 指标 | 使用同一测速数据模型，接入授权国际端点；与低流量延迟测试分开设定计划 |

页面名称约定：**回程 = VPS→大陆，去程 = 大陆→VPS**；测速标题同时写出方向，避免与客户端所在位置混淆。国际「上行/下行」统一以被监控的 VPS 为参照。

实际页面还确认了三点：国际延迟、IDC 延迟、国际测速各自有轮次和更新时间；路由的去程和回程并不必然来自同一城市、同一时刻；「十个色块」是本轮采样序列，不是十个历史轮次。

仅凭页面仍不能确定：测速有没有人为限速、实际端点容量、去程来源是否自有、所有国际延迟的底层协议和主延迟数值的统计方式。截图中大量约 10 Mbps 的结果不能证明测试限速，也不能证明 VPS 只有 10 Mbps。实施前应确定 Aster 自己的可验证口径，而非猜测参考站的私有实现。

## 3. 当前实现可以复用什么，还缺什么

| 部分 | 可复用的当前实现 | 必须补齐 |
| --- | --- | --- |
| 接入与配置 | 一键安装、独立凭证、出站领取任务、VPS/分组继承、多个每日时刻、IANA 时区 | 模块化报告预设、自动端点分配、集中测量资源目录、覆盖预览 |
| 路由 | NextTrace、traceroute 兜底、ASN 补查、公共去程、授权大陆 worker | 完整 MTR 逐跳统计、同一轮配对、按 AS 展开/折叠、多地区矩阵、带证据的线路识别 |
| 测速 | 认证临时 iperf3 服务、单/多连接、两个方向、接收端汇总与流量 | 逐秒接收端数据、TCP RTT、每方向发送端重传口径、公共 HTTP 测速适配、国际端点目录 |
| 国际 | 31 个网站/API + 8 个 CDN + 9 个原首页，共 48 个目标；HTTPS 阶段和十次 TCP 建连汇总 | 十次原始样本、AWS 地区、Telegram DC、IDC 目录、统一延迟矩阵、地区测速 |
| 历史与展示 | 实例页入口、报告抽屉、七天明细、九十天汇总、导出 | 模块轮次、完整分页、轮次完整度、矩阵和曲线展示；BGP 新采集与存储 |

几个会直接影响重构的代码事实：

- `runner/native.py` 的 MTR 目前只保留最后响应跳点的汇总，不能直接生成截图中的整张 MTR 表。NextTrace 与后续 MTR 属于两次测量，不能按 TTL 直接拼成一次报告。
- runner 已输出 iperf3 区间速率，但 `src/services/nativeObservatory.ts` 的测速子对象没有声明这些字段，解析会丢弃；这些区间也尚未统一到接收端口径，TCP RTT 尚未采集。
- `tcpQuality` 保存十次建连的汇总，没有十个单独样本，旧数据无法真实恢复成十个色块。
- `pairId` 没有轮次 ID；目前靠接近的时间寻找反向路径，可能混入其他轮次。
- 明细 API 为路线、测速、网站各返回最近 200 条，仍没有完整分页。一轮若包含大量新目标，不能靠这个窗口保证整轮显示。
- 全速任务全局串行，排队期限通常二十分钟；多 VPS、多端点成组测试会超出这个窗口。现有每日整文件读写和容量限制也不适合直接扩大到完整国际目录。
- ASN 补查是响应 IP 的 Origin ASN 资料，不是截图中的 BGP AS_PATH；当前没有 BGP/RPKI 快照采集。

## 4. 各类测量的实现方式

### 4.1 路由：完整 MTR + 来源明确的双向测量

VPS→大陆：以 **MTR 作为逐跳统计的主数据源**，TCP 与 ICMP 分开测量。固定周期、最大 TTL、端口和地址族，保存整份 JSON/原始输出和所有跳点的统计。MTR 的官方接口支持 JSON 和逐跳统计，适合生成此类表格。[MTR 官方手册](https://github.com/traviscross/mtr/blob/master/man/mtr.8.in)

每跳 IP 的归属可复用当前 ASN 缓存补查。若用 NextTrace 补充地理资料，按实际 IP 关联并记录独立查询时间；不能把另一次 NextTrace 的跳序当作这次 MTR 的跳序。只有 traceroute 能运行时，显示「单次路径追踪」，隐藏未采集的 MTR 指标。

大陆→VPS 有两个接入方式：

| 来源 | 用户操作 | 可以保证什么 |
| --- | --- | --- |
| 公共 MTR 服务 | 填好/自动识别 VPS 公网目标，选择预设 | 取得当次实际匹配的大陆来源；缺少地区/运营商时明确缺少覆盖 |
| 自有或合作测量点 | 管理员集中登记一次，以后所有计划复用 | 固定来源、长期比较；端点可达时做同端点双向对照 |

Globalping 已支持 `mtr`、TCP/ICMP、端口、包数，并返回逐跳统计。当前适配器只使用 traceroute，应增加 MTR 适配；公共服务的匹配、配额和可用性仍需校验，不能承诺九个固定三网测速端点。[Globalping 官方 MTR 文档](https://blog.globalping.io/run-mtr-with-http-using-globalping-api/)

线路标签采用三层：**运营商/网络归属 → 观察到的 AS 路径特征 → 可解释的线路推断**。例如显示「观察到 AS4809」，点击可看证据、方向和规则版本；只有证据足够才显示「疑似 CN2 GIA」。不能单凭 AS4809 给所有目标贴 GIA 标签，也不能把目标运营商等同于跨境承载网络。

「按 AS 折叠」只合并连续、归属一致的已知跳段，保留未知段和多 IP/ECMP；展开仍可看所有原始跳。不能把多跳丢包率相加，也不能把折叠结果冒称完整 BGP 路径。

未响应的延迟显示 `—`。中间跳点的探测未响应可能来自回包限速，不能单独判断业务丢包；终点需确认到达，再展示端到端探测质量。参考站显示的 `0.0 ms` 和未经区分的「丢包」不应照搬。

### 4.2 测速：单连接为主，同时支持 HTTP 和 iperf3

统一的是报告结构，不强制所有端点使用同一个测速工具。

| 模式 | 能做到的结果 | 适用范围 |
| --- | --- | --- |
| 公共 HTTP 下载 | 大陆端点→VPS 的单连接接收速率、每秒曲线、连接信息 | 提供公开测试文件且允许该用途的目标；无需家庭探针 |
| 授权 HTTP 双向 | 下载与上传的真实传输样本 | 有明确测速用途、上传接口和使用条件的服务；上传接收字节是否得到确认单独标注 |
| 授权 iperf3 双向 | 两方向接收端吞吐、发送端 TCP 指标 | 自有、合作或明确开放且参数满足要求的公共服务器 |

本次核对的 TcpQuality 提交 `c2295ae096437859ce4bbc36f170428fcac47be9`，大陆测速使用 TOS HTTP 端点、固定目标 IP 并保留 Host/SNI；包含下载和上传逻辑，候选节点来自远端目录。国际测试另有 iperf3 路径，默认带限速。因此「照搬整个脚本默认运行」不能满足用户希望的不限速和统一结构化报告。[核对的上游代码](https://github.com/ibsgss/TcpQuality/blob/c2295ae096437859ce4bbc36f170428fcac47be9/runTcpQuality-core.sh)

这提供了一个比「必须先装九台大陆探针」更省操作的候选方向：先评估现有公开测速服务的覆盖与用途，再用自主实现的标准 HTTP 采集器接入。端点可连接，不代表允许定时批量 PUT/DELETE 或不限速测试；目录需记录明确用途与条件，无法确认的目标不自动启用上传。TOS/云入口上的运营商标签也需核查，不能把云端口样本宣称为当地家庭宽带体验。

默认报告使用 **一条 TCP 数据连接**；4/8 连接作为高级选项独立展示。HTTP 模式固定 HTTP/1.1、禁止额外并行下载，记录连接次数和重定向；iperf3 使用 `-P 1`，两个方向依次执行。Aster 不设置吞吐速率上限；若公共端点存在服务端限制，标注限制并提供可切换的授权端点，不能去掉限制标记后声称获得端口极限。

建议默认每方向十秒有效采样，可选是否另加两秒预热；时间、连接数、拥塞控制、实际端点、工具版本、预热和限制全部写入报告。取消带宽限制不会取消 CPU、接入带宽和服务端繁忙等瓶颈。

测速指标定义：

| 指标 | 口径 |
| --- | --- |
| 平均 Mbps | 有效区间内接收端应用字节 × 8 / 实际区间秒数 / 1,000,000；HTTP 上传不能确认接收量时明确采用客户端上传口径 |
| 每秒曲线 | 保留每个区间的起止时刻、字节数和速率；末尾不足一秒的区间单独标注 |
| 最大 Mbps | 最大完整一秒区间速率，不是毫秒瞬时峰值；没有完整区间则显示不可用 |
| TCP RTT | 本次数据连接的 TCP_INFO RTT，说明采样端、统计方式；不能用独立 Ping 或控制连接 RTT 冒充 |
| 重传 pkt | 对应方向的数据发送端重传段数；缺少远端信息则 `—`，不用整机 nstat 增量代替该连接 |
| 流量 | 实际发送/接收字节；附预热和重试耗用，以便核算 |

iperf3 支持区间数据、JSON、反向传输和取服务端输出；但区间来源随客户端/服务端角色变化。实现时须获取对应接收端的区间信息，双端输出交叉校验，而不是把客户端区间一律视为接收端曲线。[iperf3 官方文档](https://software.es.net/iperf/invoking.html)

大陆 NAT 设备可主动连接 VPS 的临时认证监听服务，连接建立后能测两个流量方向，不需要家庭公网 IP；VPS→家庭设备的独立路由追踪仍需要可达目标。Windows/Mac 用户首先可使用公共/合作端点；自有探针的跨平台安装另行扩展，不应成为启用公共报告的前置步骤。一台家庭设备只代表自身接入网络，不能生成另外两家运营商的实测数据。

HTTP 上传优先使用专门的授权测速接收器，丢弃测试数据并返回接收字节数，避免依赖公共对象存储的写入和清理。传输测量使用单调时钟，记录双方版本及负载；同一组对比应保持时长、预热、连接数和方法一致。

### 4.3 国际：四个延迟分组 + IDC + 国际测速

| 目录 | 首期来源与规则 |
| --- | --- |
| AWS | 按官方区域服务端点维护目录，首期选亚洲、欧洲、北美代表区域；核验后扩充。注明服务和 region code，全球入口不能当作固定地区节点 |
| 网站 | 复用现有 31 个网站/API；目标名、域名、解析 IP、采样方法、ASN 保留在每轮快照 |
| CDN | 复用现有 8 个 CDN 的静态资源入口；附近 CDN 命中只说明这次访问体验，不说明骨干远距离时延 |
| Telegram | 单独维护 DC1–DC5 的可用接入地址，区分 IPv4/IPv6、端口和地址用途，不用 telegram.org 代替 DC |
| 常见 IDC | 从商家官方 Looking Glass/测试地址及明确开放的公共目录建立商家→机房→端点关系，健康检查后上架；不以全网 IP 扫描建立目录 |
| 国际测速 | 初期选香港、东京、新加坡、悉尼、美国东西部、欧洲代表授权端点，逐步覆盖截图十个地区；测速权限与延迟探测权限分别记录 |

AWS 有区域和全球端点，需逐项核对区域服务可用性与中国区域独立域名；不按截图城市名机械拼域名。官方服务端点的轻量建连测试不等于需要购买该地区 EC2，也不等于获得该地区的免费测速服务器。[AWS 区域端点说明](https://docs.aws.amazon.com/general/latest/gr/rande.html)

Telegram 的当前 DC 地址可参考官方 `help.getConfig` 的 `dc_options`，配置有有效期；它不是一个直接可用的普通 HTTP JSON 接口，需要正确实现协议或维护经核对的目录快照。TCP 可达不能证明 MTProto 业务登录、流媒体或地区解锁可用。[Telegram 数据中心说明](https://core.telegram.org/api/datacenter)、[配置接口](https://core.telegram.org/method/help.getConfig)

首期低依赖采样可复用 **TCP 建连**，保存十个原始结果；标题写「TCP 建连延迟」和「建连失败 x/10」。如增加 `nping` 裸 SYN 或 ICMP，作为另外的测量方法保存，写「探测未响应 x/10」，并区分拒绝/RST 与正常响应。不能把多种协议的数据合并成一条丢包趋势。参考站界面写「丢包」，但其可访问性说明为「十次握手中失败」，仅凭此无法认定它测量的是包级丢包。

每个目标主卡片显示明确命名的延迟统计（建议中位数，避免偶发长尾盖过常态）；详情同时给出均值、最小/最大、样本数和失败原因。十个色块分别对应本轮十次尝试；悬停、点击和键盘焦点能读到数值与状态。超时红色、未采样灰色、延迟使用固定区间并配图例，不能只用颜色表达结果。HTTPS/DNS/TLS/HTTP 状态继续保留在详情中，与网络采样分开。

### 4.4 BGP：新增独立的公开路由数据采集

先找 VPS 公网 IP 对应的最长匹配路由前缀，再采集该前缀的 Origin ASN、AS_PATH、采集器、peer 和时间。BGP 是控制平面观测，MTR 是主动数据平面探测，两者可以并排解释但不能相互替代。

- RIPE RIS：使用 RIPEstat BGP State 获取快照；需要时间窗口事件时用 BGPlay。官方数据包含前缀、AS 路径和 collector/peer 标识。[BGP State](https://stat.ripe.net/docs/data-api/api-endpoints/bgp-state.html)、[BGPlay](https://stat.ripe.net/docs/data-api/api-endpoints/bgplay.html)
- RouteViews：官方 API 可返回前缀和 reporting peers，包含 collector、AS_PATH、时间；当前仅覆盖其部分采集器，游客访问有速率限制。首期使用 API 并自己保留周期快照，不必先搭建全量 MRT 解析服务。深入历史才考虑 MRT/独立采集进程。[RouteViews 官方 API](https://api.routeviews.org/docs/)
- RPKI：按实际前缀和 Origin ASN 验证，保存有效/ASN 不匹配/长度不匹配/未找到 ROA及查询失败。它验证路由起源授权，不能证明整个 AS 路径安全或线路质量。[RIPEstat RPKI Validation](https://stat.ripe.net/docs/data-api/api-endpoints/rpki-validation.html)

同一前缀多 VPS 共用采集缓存；图表按真实路径构建，点击边可看到支持它的路径和观测点。处理 AS prepend、多 Origin、AS_SET、未知数据和覆盖前缀；不能把不同路径的边拼成一条从未被观察到的线路。

变化按相同来源与覆盖情况比较，显示「观测到的相邻 AS/路径变化」。BGP 相邻 AS 不能单凭公开路径证明付费 transit、商业直连或实际出口；Tier 1 标签要有独立分类来源和更新时间。首次快照显示记录起点，不能生成此前的上游变动。RIS 与 RouteViews 的采集时刻和 peer 路由更新时间分别保留，不虚构它们是同一秒的全球快照。

## 5. 产品结构与最低操作量

建议实例页结构：

```text
实例详情 / 网络报告
  最近完成时间 · 探测器状态 · 本轮完成度       [立即检测] [定时计划] [⋯]
  路由 | 测速 | 国际

  路由：回程 MTR → 去程 MTR → BGP 快照与变化
  测速：大陆九宫格覆盖摘要 → 双向单连接速率表 → 测量条件
  国际：AWS/网站/CDN/Telegram 矩阵 → IDC 矩阵 → 国际双向测速

  每个模块：最新/历史轮次 · 来源与协议 · 完成/失败/缺少覆盖数
```

保留 Aster 的颜色、字体、留白、圆角和深色模式，不复制参考站品牌。桌面国际卡片按可用宽度排 3–4 列，手机 1–2 列；MTR 允许表格区域横向滚动并固定跳号/归属列；测速手机优先显示目标、曲线和平均值，其他指标可展开。BGP 有全屏和路径列表备选视图。顶部只留主要操作，其他操作放入菜单，避免长工具栏遮挡管理入口。

**配置只用三步：**

1. 选模块和预设：「大陆线路」「大陆单连接测速」「国际基础」「国际完整」；地区、运营商、商家在目录中勾选，自动填入端点。
2. 选周期：每个模块独立频率，也可每天多个时刻；显示时区、下次执行和流量估算。
3. 选当前 VPS、多台 VPS 或分组：预览逐台的可用覆盖、缺失资源、工具状态和预计排队时间，然后保存。

默认建议为国际延迟每三十分钟、路由每六小时、BGP 每六小时；全速大陆/国际测速为管理员明确启用后的每日指定时刻，可选平峰/晚高峰两个时刻。公共来源更严格时自动遵守其条件。允许用户修改，但不让每十五分钟的网站采样连带触发高流量测速。

资源接入与报告设置分开：管理员在「测量资源」集中维护探针、公共服务和授权端点，实例页展示「可用 6/9，缺少北京联通等三项」及接入入口。没有资源的行显示原因和补齐方式，不显示 0 Mbps、不永久转圈，不要求先接入家庭设备才能看到国际和回程报告。

批量配置延续当前分组继承与节点覆盖机制。一次预设绑定新节点；重叠方案去重，同节点、同端点、同口径、同计划触发不重复测量。可一键恢复推荐目标、只选可用目标，支持搜索和地区/运营商筛选；自定义主机放入高级选项。

## 6. 数据、调度与兼容方案

### 6.1 以模块轮次组织数据

| 对象 | 关键内容 |
| --- | --- |
| Endpoint | 稳定 ID、来源、商家/分类、地区、运营商声明及验证资料、地址/端口/协议、允许用途、限制、健康状态、目录版本 |
| Suite | 模块、选中目标、参数、各模块周期、VPS/分组范围、继承规则 |
| Batch | 点击「全部立即检测」生成的父执行 ID，关联各模块轮次；不要求它们同时完成 |
| Round | 唯一 ID、VPS、模块、计划触发时刻、开始/完成时刻、参数及端点快照、预期结果槽位、完整度、状态 |
| Measurement | roundId、槽位 ID、实际来源与目标 IP、测量开始/完成时刻、方法、工具版本、原始样本/MTR 跳点/速率区间、异常 |
| BgpSnapshot | 前缀、Origin、来源、采集时间、peer 的路由时间、AS_PATH、RPKI、覆盖与上一快照变化 |

周期触发生成一次模块 Round，随后拆成执行任务；下发前固定端点和参数快照。去程/回程配对键包含 roundId、端点对、地址族和协议，只允许同轮对照。相同时间但不同来源的公共样本保留为独立参考。

状态包含等待资源、排队、运行、完整完成、部分完成、失败、取消；缺少资源的槽位会收尾并写明原因。每模块独立轮次选择器，默认最近完整轮；进行中的轮次可展开进度。若显示「各目标最新结果」概览，必须显式标注它并非同一轮。

### 6.2 插件内完成常规采集，不先新增后台服务

主题负责交互和渲染；插件负责目录、轮次、调度、公共 API、鉴权与存储；runner 负责本机网络测试；可选大陆/国际 worker 提供固定测量来源。BGP 首期通过插件异步 API 适配，不新增 VPS 常驻采集器。

任务、心跳和报告经过 Komari；测速数据在 VPS 与端点之间直接传输，不能经过浏览器或 Komari 面板代理，否则测到的是代理路径和面板带宽。新端点在测量前验证公网地址、允许用途与地址族，轮次固定实际测量 IP；端点发生改变则保留变化原因，不把备用地址静默算成原端点。

在现有仓库增加报告 API 新命名空间，例如 `/v3/...`，旧 `/v1` 和 `/v2` 保留。主题先查询 capabilities，再展示可用模块；旧 runner 不领取不支持的新操作。具体 API 命名在阶段一冻结，不把文档示例当作已存在接口。

首期采用插件自身的 **每轮独立明细文件 + 按节点/模块/日期的小型索引**，写入用临时文件与原子替换，回传按 jobId/attemptId 幂等。读取一个轮次不必加载七天全部日报；提供游标分页，保存模块汇总与覆盖计数。索引可从轮次文件重建，并验证 Komari 1.4.3 的路径处理。

不直接假定 Goja 插件支持 Node 原生 SQLite 扩展，也不改 Komari 自己的数据库。确有规模压力后，再引入随安装器管理的 Python/SQLite 存储进程；只有 API 缓存不足、需要大范围历史 MRT/流式 BGP 时才引入独立采集服务，不作为基础安装依赖。

旧报告只作为「旧版单次检测」读取，不补造十次样本、每跳 MTR、TCP RTT 或历史轮次。旧计划、密钥和凭证保留；用户可按预览迁移成新 Suite，迁移时停用被替代的旧触发，防止重复测速。详情保留期与汇总保留期分别可见，过期的样本不能用均值重新画成真实曲线。

### 6.3 调度要满足成组测试容量

轻量采样与大流量测速使用不同队列；轻量测试采用有限并发，吞吐任务按 VPS 与端点资源预留串行，独立无冲突资源在容量允许时并行。测速时该 VPS 上的其他高流量检测不启动，关联延迟样本注明负载条件或避开测速时段。

排队期限与执行租期分开：前者按预测排队量和计划有效窗口计算；后者由心跳更新并限制最晚执行时刻。上一轮未结束时，按计划策略跳过/合并一次触发，不无限积压。支持取消、繁忙端点退避、部分完成，失败重试与结果回传重试分开，回传重试不再次发送测速流量。临时监听服务无论取消、崩溃还是超时都自动关闭。

公共 API 统一限额、缓存、超时和退避，网络请求在状态锁外执行；同一公网前缀的 BGP 查询复用结果。容量预览按整台 VPS 的全部方案累计计算，不能只校验单方案，也不能仅扩大当前 64 目标、9000 报告/天的限制。

## 7. 分阶段实施与验收

阶段一是全部后续能力的前置基础；国际延迟优先交付可见收益，路由与测速分别验收，BGP 不阻塞已有报告。

| 阶段 | 主要交付 | 依赖与验收门槛 |
| --- | --- | --- |
| **一：冻结口径与报告基础** | 模块指标合同、端点目录规范、Round/Batch、能力协商、轮次 API/分页、队列收尾、Aster 报告布局和预设配置 | 同一轮不混入其他轮数据；失败/缺少覆盖能收尾；旧版本可读；首次保存、插件重启、重复回传、跨天和夏令时正确 |
| **二：国际延迟与 IDC 矩阵** | 四个国际分组、十次原始样本、色块卡片、可选 IDC 目录、HTTPS 详情、独立历史轮次 | 十块与原始数据逐项一致；DNS 失败/拒绝/超时/403 分开；目录来源可查；IPv6 缺失不伪造结果；完整轮次不受 200 条窗口截断 |
| **三：完整双向 MTR 报告** | 回程地区三网切换、公共 MTR 去程、固定来源适配、逐跳/AS 折叠、线路证据、路径变化 | 本机及公共 MTR 与原始输出一致；去回程同轮配对严格；中间跳不响应不误报业务故障；缺少地区不自动换成别的地区却保留原标签 |
| **四：大陆与国际单连接测速** | HTTP/iperf3 适配、九个大陆目标矩阵、国际地区矩阵、双向区间曲线、TCP RTT/重传、全速计划与资源预约 | 先小规模授权端点验证，逐步补齐覆盖；一条数据连接、无 Aster 速率上限；双端速率一致；单位正确；负载不污染重传；NAT、繁忙、取消和断线正常 |
| **五：BGP/RPKI 快照** | RIS 与 RouteViews 来源适配、图/路径表、采集器和 peer 统计、前缀/地址族切换、变化历史、RPKI | 每条边可追溯原始 AS_PATH；最长匹配与覆盖前缀分清；单来源失败显示部分覆盖；多 Origin、prepend、未找到 ROA、首次无历史正确 |
| **六：迁移和完整生产验收** | 批量迁移预览、旧计划去重、报告分享/导出、安装与排障文档、分批升级和发布 | 官方 Komari 1.4.3 + 新版兼容；关闭 Web SSH 仍工作；深浅主题/390px/键盘完整；多 VPS 队列与保留期压测；真实三网和国际端点验收后才宣称完整覆盖 |

每阶段完成时更新 capability 和报告说明，按实际交付发布，不用空白图或假数据预告未完成能力。若某些大陆端点尚未取得，阶段四仍可交付可用的测量引擎和部分矩阵，但必须写明覆盖范围，不能称三地三网的九个目标已全部完成。

建议首个可体验版本包含 **阶段一 + 阶段二**，并保留旧路由/测速读取入口：用户立即能看到符合参考站组织方式的国际报告，后续接入完整 MTR 和单连接测速时不再重做数据模型。

## 8. 验证设计与规模边界

| 验证层 | 必测内容 |
| --- | --- |
| 指标/协议 | 十次样本中的失败不进入成功延迟均值；Mbps/MB/s 换算；接收/发送方向；一秒区间与残段；TCP_INFO 对应数据连接；未采集不是零 |
| 集成 | MTR JSON/版本差异、NextTrace 补查按 IP、iperf3 双端 JSON与认证版本、HTTP 固定 Host/SNI和限量传输、公共 API 429/无覆盖、RPKI 多状态 |
| 调度/存储 | 重启恢复、任务唯一性、取消/清理临时服务、过期收尾、跨轮配对、并发心跳、分页、索引重建、保留期和磁盘容量 |
| UI | 大矩阵、缺失/部分完成、逐跳/AS 切换、历史轮次、深色/浅色、390px、键盘操作、复制和导出；图的可访问路径表 |
| 实网 | 至少实际电信/联通/移动各一个明确来源，先完成双向，再扩展到北京/上海/广东九格；国际区域和端点负载有记录。公共/机房/家庭来源分开验收 |

实验室可模拟丢包、时延、拥塞、CPU 瓶颈、服务端限制和故障，用来验证程序；不能把 Docker 本地两端结果或代理 DNS 映射结果当作大陆/国际实网覆盖证明。阶段六的多 VPS 验收需包含超出旧二十分钟队列窗口的工作量，以及国际矩阵超过旧类别历史窗口的情况。

建议一期验证规模：单 VPS 150 个延迟目标，每目标十次采样、每三十分钟一轮；再做 50 台 VPS 的调度/索引压力验证。它们是待实现的容量验收目标，不是当前版本已保证的能力。默认不全选所有 IDC/所有地区，按实际选中的商家和目标生成轮次。

## 9. 免费资源、实际成本与实施取舍

不需要强制购买商业测速 API。MTR、iperf3、curl 等可用于自主采集；公共 BGP 数据和域名目标可提供基础报告。第三方公开目标目录、托管测速节点和商业测量点是可替换资源，需记录来源、允许用途与健康状态。全部代码继续在当前 Aster 仓库维护，暂无另开仓库的必要。

TcpQuality 当前提交的仓库根目录未发现独立 LICENSE 文件，GitHub 许可证字段为空。本方案引用目标事实和公开测量思路，不把它视为可任意复制分发的已授权依赖；若要直接内置代码或扩展其托管节点用途，先核对维护者提供的许可和接口条件。已有脚本适配不应成为新版结构化报告的唯一数据通道。

**不限速与控制执行规模可以同时成立：**限制每次时长、每天轮数和同时占用端点数，超过预算时停止后续测试并显示停止原因；不能暗中限速后把结果当作真实上限。按实测字节核算，给用户显示累计流量。

仅作量级示例：若一个目标上下行均实际达到 1 Gbit/s，各有效测十秒，则约 2.5 GB；九个大陆目标约 22.5 GB/轮，十个国际目标约 25 GB/轮。两套每天各一轮、按三十天计约 1.425 TB/VPS；预热、重试、协议开销另计。真实使用量由实际速度与执行范围决定，多 VPS 会成倍增加。选择公开测速对象不能替代端点自身的使用条件和容量限制。

实施取舍采用同一个产品、按可用资源展示覆盖：没有固定大陆探针时，先启用国际矩阵、VPS 回程 MTR、公共去程参考和允许使用的 HTTP 测速；取得合作/自有端点后，补齐固定双向路由与不限速三网测速。这样用户能先得到有用报告，也能明确看见距离完整目标还缺哪些实际资源。
