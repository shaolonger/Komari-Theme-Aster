# 原生网络观测：大陆双向线路、全速测速与国际网站

Aster **v1.6.0**、插件 **v1.5.0**、runner **v1.5.0** 新增原生观测。支持 Komari **≥1.4.3**，不修改 Komari/Agent 核心，Web SSH 可保持关闭。检测是带时间和来源的定时样本，不是持续获知所有真实业务包经过的线路。

## 快速更新

1. 在 [Release](https://github.com/shaolonger/Komari-Theme-Aster/releases/tag/v1.6.0) 下载并更新主题 ZIP 和插件 ZIP，启用插件并批准 API 路由与系统 RPC 权限。HTTP 响应上限为 8 MiB，用于读取 Globalping 全局目录；只保存大陆部分，runner 请求体仍限制 128 KiB。
2. 在每台 VPS 的 **实例详情 → 网络检测 → 管理探测器** 复制“一键安装 / 升级”命令并执行。未重置密钥时回车保留；仅更新面板不能更新 VPS 上的 runner。
3. 三个原生类别显示在实例页；旧 NextTrace、公开 iperf3 与 TcpQuality 计划、图片和历史在 **工具诊断与旧计划** 中，原有固定 UTC 时差不会被改成 IANA 时区。不要同时保留重复的高流量测速方案；不再需要的旧计划可暂停。

## 先启用国际网站（无需大陆探针）

1. 点 **设置检测方案**，选择 **国际网站**。
2. 第二步默认勾选六个推荐网站，可选择 Google、YouTube、GitHub、Cloudflare、Wikipedia、Microsoft、Apple、Amazon、Netflix、Reddit、OpenAI、Bing；也可一次填入自有域名。选择本机、多台 VPS 或分组。
3. 第三步默认每 15 分钟。可选 IPv4/IPv6、间隔或每日多个时刻；例如 `03:00, 21:00`，时区选 **北京时间 · Asia/Shanghai**。预览显示覆盖和下次执行时间，然后保存。
4. 在 **管理原生方案** 或实例类别的计划中点 **立即检测**。查看 DNS、TCP 建连、TLS 握手、累计首字节耗时、HTTP 状态、连接 IP。

403/401 显示应用响应，不能等同于网络不通；超时/解析/TLS 错误有独立诊断。先用 HEAD；网站返回 405 时使用限制下载大小的 GET。不会绕过 TLS 验证。当前配置使用 HTTPS 默认路径 `/` 和端口 443，网站重定向本身记为可收到响应，不自动追随。命中附近 CDN 只代表该网站体验，不代表美国/欧洲线路。IPv6 必须由 VPS 和目标同时支持。

## 公共大陆去程与三网回程参考

1. 选择 **大陆线路**，保留“Globalping 大陆公共去程与 NextTrace 北京三网回程参考”。
2. 在 **测量点接入与 VPS 公网地址** 核实每台 VPS 的连接目标。能读取 Komari IPv4 时自动带入；否则只填一次公网 IP/域名。IPv6 计划需使用 IPv6 地址或支持 IPv6 的域名；不符合地址族时会标记缺少覆盖。
3. 第二步查看公共目录的大陆电信 AS4134、联通 AS4837、移动 AS9808 候选数量、城市。目录标签由提供方标记，动态变化，不保证所有城市或运营商当时在线；区域接入 ASN 不一定属于这三个骨干 ASN。
4. 默认每小时检测；保存后立即执行。插件每分钟领取公共结果，通常需要 1–2 分钟。每份报告保存实际返回的国家、城市、ASN、网络、接入标签；返回来源不符合请求条件时显示缺少覆盖。

方向统一写为 **大陆→VPS**、**VPS→大陆**。Globalping 三个公共去程与 NextTrace 北京公开目标的回程是**独立参考样本**，不是相同端点对的双向线路。公共服务支持路径测试，不支持本项目的 iperf3 全速测速。开启公共探针会将目标地址和测量结果交给 [Globalping](https://globalping.io/)；只用自有探针时取消该选项。无需 API token；本项目每小时最多提交 120 次公共测量（每个 VPS 的三网去程为三次），429 后退避一小时；同出口的其他调用仍可能占用上游额度。无匹配探针（422）显示缺少覆盖，不显示 0 延迟或网络差。

## 自有大陆探针：固定端点双向线路

1. 准备你拥有或获授权的 Linux systemd 设备，例如大陆电信、联通、移动各一台。家庭宽带与机房样本分开记录。设备带宽、CPU、接入类型会影响结果，软件无法代替实际测量资源。
2. 在方案面板展开 **测量点接入与 VPS 公网地址**，填写探针名称、城市、运营商、接入类型。城市/运营商为管理员声明，不是系统保证地理位置。能从 VPS 到达的公网地址可填写；NAT 后留空即可。
3. 点 **生成大陆探针凭证**，立即复制仅显示一次的密钥和一键命令。在该大陆设备执行命令，将密钥粘贴到隐藏输入提示。
4. 等待约 30 秒，刷新后显示在线。在大陆线路方案勾选该探针。只用固定端点时取消公共样本。
5. 保存并立即执行。报告将分别显示大陆探针→VPS、VPS→该探针的实际响应跳点，在接近时间的同端点报告间展示双向对照。默认 TCP 443，可选 ICMP；最多 32 跳、每跳三次查询，NextTrace 失败会同协议回退到系统 traceroute。MTR 可用时用 20 次短时测试记录最后响应跳点；未确认终点的损失不会标成终点业务丢包。

大陆探针配置保存为 `/etc/aster-network-observatory/probe-<探针 ID>.json`，对应服务是 `aster-network-observatory-probe@<探针 ID>.service`。它可与本机原有 VPS runner 服务共存，安装不会覆盖 `agent.json`。升级后需重跑对应命令重启各角色。查看日志：

```sh
sudo systemctl status 'aster-network-observatory-probe@<探针 ID>' --no-pager
sudo journalctl -u 'aster-network-observatory-probe@<探针 ID>' -n 100 --no-pager
```

NAT 后探针能主动连接，所以去程和反向流量测速仍可用；VPS→探针的完整逐跳线路可能缺失，报告明确标记。中间跳点未响应、ICMP 限速或某个 ASN 出现，不足以断言业务丢包或整条线路属于 CN2 GIA 等等级。撤销探针凭证立即阻止后续鉴权；只依赖该探针且没有剩余来源的计划会暂停，旧报告保留。

## 大陆↔VPS 全速测速

1. 先接入至少一个授权大陆探针；两端需要带 RSA 认证支持的 iperf3，VPS 另需 openssl。一键安装器会安装依赖；若软件源的 iperf3 不支持认证，预览/结果会提示，不能退成未认证监听。两端系统时钟应同步。
2. 在 **VPS 连接目标与临时测速端口** 确认公网地址和端口，默认 TCP `25201`，可选 20000–40000 中一个固定端口。
3. 在 VPS 本机防火墙和云安全组允许该端口，优先只允许大陆探针出口。例如使用 UFW 时，按自己真实探针出口替换下列占位符：

   ```sh
   sudo ufw allow from <大陆探针出口 IP> to any port 25201 proto tcp
   ```

   安装器不会自动改你的防火墙。若公网地址经 NAT 转发，需把同一端口转发到 VPS；IPv6 则检查 IPv6 防火墙。不要把 HTTP 反代端口当成原始 iperf TCP 端口。
4. 选择 **大陆测速**，勾选大陆探针和 VPS。默认每个方向 10 秒、分别测试单连接和 4 连接；可选 5–20 秒，单连接/4/8 连接组合。确认有权使用两端且接受实际流量。
5. 默认每天北京时间 21:00，可追加 03:00。预览流量和覆盖后保存，再立即运行。
6. VPS runner 临时启动带认证的监听，生成一次性 RSA 公钥和会话口令；大陆端主动连接，先大陆→VPS，后 VPS→大陆，串行测试连接配置。TCP 不设置 `-b`/带宽上限，不剔除预热区间；保存接收端速率、字节、时长、重传和实际对端地址。全局同一时间最多一个原生全速任务，旧高流量工具任务也参与互斥。
7. 完成、撤销或超时后关闭监听；即使面板网络断开，本地最多 240 秒自动关闭。会话私钥和口令不进入报告/管理员目录 API。认证用于防止未获授权的测速连接，不会加密 iperf 测试数据。

这是“该测量点、该时刻、两端条件下的实测吞吐”，不是 VPS 标称端口的保证值。单连接更接近一次传输，多连接观察并发吞吐。若双向都达到 1 Gbit/s，每方向 10 秒约 2.5 GB；同时测单连接和多连接约 5 GB/探针/VPS，每天一次约 150 GB/月，两端均有流量。实际以接收端报告字节为准。大陆三网的稳定测速资源需要自有设备、宽带、服务器或授权，不保证“免费公共节点无限速且长期可用”。工具没有必需收费依赖。

## 批量、报告和历史

首页选择多台 VPS 后点 **网络检测**，同样进入三步原生方案。分组继承保持开启，新加入分组的 VPS 在下次到期时自动纳入；关闭继承则保存当次匹配的 VPS 快照。相同设置重复保存不会重复创建方案。集中方案的编辑/暂停/恢复/删除在 **管理原生方案**；编辑集中方案会作用于其完整范围，单机另建方案时请先检查重叠范围。

原生类别展示来源×方向的覆盖卡片、最近样本时间、数据过期、缺少覆盖与检测失败。打开卡片可查看网站阶段、双向路径、单/多连接测速、同来源和参数的每日趋势，并导出 PNG 或完整 JSON。PNG 是摘要，完整跳点和诊断在 JSON 中。当前屏幕最多显示最近 200 份详细报告；7 天的详细文件与 90 天每日汇总按 VPS/日期分区存储在插件数据目录 `native-reports/<UUID>/`，原生计划/探针状态在 `native-state.json`。每日报告最多 10000 份以防无界增长，超出停止写入并报告错误；将上述目录与旧 `state.json`、历史和图片一起备份。

旧工具历史没有改写成原生测量；来源和参数不同不会混算趋势。IANA 时区内置常用九个时区的 2020–2040 过渡表，支持夏令时；缺失的春季时刻跳过、重复的秋季时刻可能执行两次。时区法规变化后应升级过渡表。原有固定 UTC 时差计划仍按旧规则运行。

## 验证边界

测试包含原生 API 鉴权、受控两端会话、公共异步 ID/限额/无覆盖、分组继承、夏令时、报告保留、旧功能回归及浏览器桌面/移动端。Linux 容器中执行了真实 curl、NextTrace、MTR 与两端认证 iperf3；未认证连接被拒绝，两个方向和单/多连接均返回实际接收统计，本地定时回收通过。另向 Globalping 提交一次 CN/AS4134 的真实路径测试，返回广州电信机房来源的 20 跳不完整样本，未伪装成到达目标。实验容器及公共参考目标不是用户实际 VPS；完整三网覆盖和速度需在接入自己的测量点后验证。

# Aster 网络检测：从安装到批量巡检

Aster v1.6.0 将网络检测放在每台 VPS 的**实例详情 → 节点诊断 → 网络检测**中。配置、任务状态和报告都在此处；旧 `/network-observatory` 地址只提供跳转到实例页的节点列表。Komari 1.4.3 及以上可用，不需要修改 Komari 或 komari-agent 源码，也不需要开启 Agent Web SSH。检测由每台 VPS 上独立的 systemd 探测器经出站 HTTPS 领取任务，浏览器关闭后仍会运行。

## 1. 更新主题和插件

1. 从 [最新 GitHub Release](https://github.com/shaolonger/Komari-Theme-Aster/releases/latest) 下载 `Komari-Theme-Aster-v1.6.0.zip` 与 `Aster-Network-Observatory-v1.5.0.zip`。
2. 在 Komari 后台分别更新主题和插件，启用插件。插件要求 Komari **≥1.4.3**，不是 ≥1.5.1。
3. 批准插件的 **API 路由**和**系统 RPC**权限。v1.2.0 新增系统 RPC 权限是为了在浏览器关闭时读取 Komari 节点清单和分组，完成自动继承；插件代码只调用 `admin:listClients`，不会调用远程命令执行。此权限在 Komari 层面较宽，管理员应安装自己信任的插件版本。
4. 用管理员账号刷新 Aster 页面，进入任意 VPS 实例详情，点「网络检测」。若显示插件未就绪，检查插件是否启用、权限是否批准、反向代理是否转发 `/api/aster-network-observatory/`。旧版主题与新版插件应同时升级，才能使用批量方案和实例页。

升级会保留插件原有凭证、计划和历史；无需重发探测器密钥。要修复 NextTrace 崩溃后的路径追踪和 TcpQuality 的 `TERM` 错误，**必须在每台受影响的 VPS 上重跑第 2 步的一键安装命令**，使 runner 升级到 v1.5.0（包含 v1.4.1 的修复）；只更新面板上的主题和插件不会替换 VPS 上的脚本。密钥未重置时可在提示处回车保留。全速双向测速需要主题 v1.5.0 或以上、插件 v1.4.0 或以上、runner v1.4.0 或以上。

## 2. 为第一台 VPS 接入探测器

1. 打开这台 VPS 的「网络检测」标签，点击「为此 VPS 启用检测」。页面已显示**当前节点 UUID**。它是 36 位带连字符的 Komari 节点标识；**不是** Komari Agent token，也不是下面的探测器密钥。
2. 点击「生成本机探测器密钥」，立即复制页面仅显示一次的 64 位密钥。若节点已登记，按钮是「重置」；重置会让旧密钥立即失效，须马上在该 VPS 重新配置。
3. 复制同一面板中的「本机安装 / 升级命令」，在这台 Linux systemd VPS 的 SSH 终端执行。命令已经填好面板地址和 UUID，例如：

   ```sh
   curl -fsSL https://github.com/shaolonger/Komari-Theme-Aster/releases/latest/download/Aster-Network-Observatory-install.sh | sudo sh -s -- --server-url 'https://monitor.example.com' --node-uuid 'xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx'
   ```

   如果面板部署在子路径，在页面先把地址改成完整路径，例如 `https://example.com/komari`。命令通过 SHA-256 校验下载的 runner ZIP；需要 curl、systemd 和 root/sudo。安装器按系统包管理器补齐 Python 3、iperf3、TcpQuality 所需工具，并为受支持的 Linux CPU 架构安装校验过的 NextTrace v1.7.3；TcpQuality 从上游固定提交下载并校验。已安装的工具会保留。命令中不放密钥，避免它进入 shell 历史和进程参数。
4. 向导提示「探测器密钥」时粘贴第 2 步的值。输入不会回显。询问 TcpQuality 脚本路径时，使用一键安装的版本直接回车。向导验证凭证后保存配置并启动服务。
5. 等待约 10–30 秒，实例页应显示「探测器在线」。如果只显示「等待首次连接」，在 VPS 执行：

   ```sh
   sudo systemctl status aster-network-observatory-agent --no-pager
   sudo journalctl -u aster-network-observatory-agent -n 100 --no-pager
   ```

探测器只向 Komari 发起出站请求，不需开放 VPS 入站端口。反向代理必须保留 `Authorization` 请求头。Komari Agent 的 `--disable-web-ssh` 可保持开启。每台 VPS 仍需各自的密钥和一次 SSH 安装，这是在不开启远程执行权限下确认节点身份所需的操作；后续检测目标、频率和分组继承可批量配置。

已有探测器升级时，在同一 VPS 重新运行页面给出的命令即可。地址和 UUID 已填好；若没有重置密钥，密钥提示处回车可保留原值。升级会重启 systemd 服务以加载新代码。

## 3. 一次设置多台 VPS 的检测方案

在一台 VPS 的「网络检测」标签点「套用方案 / 批量配置」。在首页 VPS 列表选中多台后，也可点「网络检测 · N 台」；管理工作室的「网络观测 → 网络检测方案」同样可用。

1. 在「选择检测」勾选一个或多个内置方案。第一次建议只选「基础 HTTPS 可用性」，无需填写目标；然后点「下一步」。
2. 在「目标与时间」设置间隔或“每天指定时刻”（最多 8 个时刻，使用固定 UTC 时差）。自有网站或 iperf3 方案可从公开候选目录选目标，也可填自有主机和端口。选择公开节点后，目标主机输入框会收起；选回“自定义目标”再手填。测速和图片报告需要确认目标使用条件与流量。
3. 在「范围与预览」勾选 VPS 或 Komari **分组**，两者取并集；可使用搜索和「选择搜索结果」。从实例页打开时默认只作用于当前 VPS，点「扩展到更多 VPS」才显示批量范围。选择分组并保留「继承方案」时，新加入该分组的 VPS 会在下一次同步（约 1 分钟）后自动取得计划，浏览器无需保持打开。
4. 点「预览应用范围」。预览逐台列出新增/已有计划、未接入、离线和缺少工具的状态。确认无误后点「确认应用」。重复按相同范围应用不会产生重复计划；尚未安装探测器的节点也能先保存计划，接入且工具就绪后才执行。
5. 返回实例详情查看本机计划、排队/运行状态和报告。新计划会错峰开始，通常先等待约 1–6 分钟；可在已接入节点点击「立即检测」加速验证。

取消「继承方案」会把当次新增计划复制为独立计划，今后不受集中更新影响。需要集中修改时，在同一面板的「管理已有方案」编辑名称、范围、频率或目标，也可整体暂停/恢复/删除。重叠范围下同一预设与目标在同一节点只创建一份计划；启用方案优先于暂停方案。某台 VPS 上直接修改继承计划后，该计划成为该机独立覆盖，后续方案更新不会覆盖它。删除继承计划会加入该机排除项；删除整个方案会删除其余继承计划，但保留单机覆盖和历史。

## 4. 选择目标、每日时刻与图片报告

方案的“检测频率”可选固定间隔，或“每天指定时刻”。后者可添加 1–8 个不重复的 `HH:mm`，并设置固定 UTC 时差，例如北京为 `+8`、东京为 `+9`。固定时差不会随夏令时自动变化；当地切换夏令时后如需保持当地时钟时刻，请手动调整 UTC 时差。插件每分钟调度一次，执行中的任务不会在同一 VPS 上叠加；探测器离线时保留到期计划，恢复后最多补做一次，再计算下一个时刻。

| 方案 | 默认目标与注意事项 |
| --- | --- |
| 基础 HTTPS 可用性 | Cloudflare、Wikipedia；只发 HEAD 请求，显示 DNS、建连、TLS 与首字节耗时。 |
| 三网路径 · NextTrace | 默认北京电信、联通、移动 IPv4。可在“路径目标”中按北京、上海、广州、杭州、合肥，运营商及 IPv4/IPv6 选择最多 24 个目标。目录取自 [NextTrace 固定版本目标清单](https://github.com/nxtrace/NTrace-core/blob/7ff73b2c51f9f37a9bc1d6139b7053948f0250db/fast_trace/basic.go)，是探测目标而非质量评级；失效目标可在方案编辑处取消。 |
| 三网回程 / 国际互联 · TcpQuality | 保留原来的纯文本诊断，不上传报告；`--route` 模式按上游定义不会产生图片。 |
| 三网质量 / 国际互联 · 图片报告 | 两个独立的可选方案。runner 用已安装且校验过的上游脚本执行标准或 `--intl` 检测，明确允许上传检测数据后，从 TcpQuality 的报告服务获取 PNG。插件将成功下载的图片存到自己的数据目录，只向已登录管理员提供同源图片接口。报告服务暂时不可用时，文字结果仍会保留。 |
| 授权 iperf3 吞吐测速 | 可填写自有主机，或从 [Leaseweb 官方公布的测速节点](https://kb.leaseweb.com/kb/network/network-link-speeds/)选香港、新加坡、东京、悉尼、欧洲或北美候选。候选可连接不代表适合频繁批量压测，须确认使用条件与流量预算。当前单连接上传 10 秒，最高 100 Mbit/s，单次最多约 125 MB；结果是限速条件下的吞吐，不能当作端口峰值速度。 |
| 全速双向测速 · iperf3 | 使用同一目标分别测 VPS 上传和下载。TCP 不设置带宽上限，4 条并行流，每方向测试 10 秒并跳过最初 2 秒的预热统计；结果显示接收端速率、传输数据量及上传重传。优先使用自有测速服务器。|

全速测速在 VPS 上执行相当于 `iperf3 -c HOST -p PORT -t 10 -O 2 -P 4 -J` 和加上 `-R` 的第二次测试。`-R` 让服务器向 VPS 发送数据；两次测试分别记录，不使用 `--bidir` 同时竞争上下行。探测器对每个方向设超时，插件全局同一时间最多运行一个全速测速任务，同一测速端口不会同时承载多个本站 iperf3 任务。**不限速不等于测得端口标称速率**：结果仅代表 VPS 到所选端点在测试时的路径、两端 CPU 和负载条件。Leaseweb 公开节点每端口一次只能处理一个测试，忙碌时可换端口或稍后重试；定时多节点测速建议部署自己的 iperf3 服务端并确认其带宽足够。若实测上下行均为 1 Gbit/s，各 10 秒约传输 2.5 GB，预热还会增加流量；每天一次约 75 GB/月，测试端同样承受这些流量。流量按结果中的实际传输字节数核算。

一键安装器支持带 systemd 的 Linux，并按 apt、dnf、yum 或 zypper 安装基础依赖。NextTrace v1.7.3 的预校验二进制支持 x86-64、ARM64、ARMv7 与 RISC-V 64；其他架构会给出明确错误，不会下载未校验程序。安装器直接从 [TcpQuality 上游固定提交](https://github.com/ibsgss/TcpQuality/tree/c2295ae096437859ce4bbc36f170428fcac47be9)取得入口和 core 并做 SHA-256 校验，不把第三方脚本重新打包进本项目；上游仓库未提供明确的许可证，使用前应核对其条款。已有手动安装的 TcpQuality 会被保留。若 VPS 软件源不可用、被包管理器锁占用或无法访问 GitHub，安装器会报错并停止，待网络或软件源恢复后重跑同一命令即可。

TcpQuality 标准检测与国际互联模式在上游脚本内要求 UID 0，因此 v1.3.0 runner 的 systemd 服务以 root 身份执行。服务仍限制为固定探测类型，并保留 `NoNewPrivileges`、只读系统目录、私有 `/tmp` 及 `CAP_NET_RAW` 能力边界；它不会启用 Komari Agent 的远程执行或 Web SSH。管理员应只从可信的本项目 Release 安装 runner，并了解第三方脚本在该服务中以 root 执行。

## 5. 查看结果、单机调整和临时检测

实例页显示探测器在线状态、依赖可用性、计划、任务和历史。点“自定义 / 临时检测”可建立本机计划，也可只执行一次。每日多时刻同样适用于本机计划和集中方案；批量方案的目标、时间或应用范围可在“管理已有方案”修改。原有计划升级后保持原来的间隔频率，不会自动改为每日时刻。

在 Aster v1.6.0 的“自定义 / 临时检测”中，选择“路径追踪”“iperf3 限速上传”或“全速双向测速”，可在“公开候选”和“自定义主机”之间切换。公开候选会自动带入目标和端口；自定义主机由用户填写。候选列表来自已启用的网络观测插件；若没有候选项，先确认插件版本、启用状态和 API 权限，再刷新实例页。全速测速需要插件 v1.4.0 和 runner v1.4.0 或以上，实例页会显示“全速双向 · 可用”。

点最近结果或历史记录可查看指标、路径和完整输出。图片报告直接显示在报告抽屉，不需要打开外部结果链接。文本历史每节点保留最多 500 条或 2 MiB；为控制磁盘，图片每节点保留最近 **20 份图片报告**，单张最大 2 MiB。更早的文本仍可查看，但对应图片会被清理。图片文件在 Komari 插件数据目录下的 `aster-network-observatory/reports/<节点 UUID>/`，请将该目录纳入面板备份。报告上传会把 VPS 出口 IP 和检测数据交给 TcpQuality 的服务；不希望上传时使用原来的纯文本方案。

## 6. 常见问题

- **NextTrace 退出码 139 / `Segmentation fault`**：139 表示 VPS 上的 NextTrace 进程收到 SIGSEGV；仅凭这行输出无法确认它在该主机崩溃的内部原因。runner v1.4.1 会保留原始诊断，并在此情形自动运行系统 `traceroute -I`；结果页会显示跳点及“备用”说明，备用路径没有 NextTrace 的 ASN 数据。安装器会确认 `traceroute` 可用。若备用追踪也失败，结果仍标记失败并保留两次工具输出；可以先在 VPS 上直接运行 `nexttrace --json --no-rdns --max-hops 16 --queries 1 <目标>`，再检查系统日志和 NextTrace 上游问题。
- **TcpQuality 退出码 1 / `TERM environment variable not set.`**：上游固定版本脚本在所有模式前执行 `clear`，而 systemd 通常不设置 `TERM`；脚本遇错即退出。runner v1.4.1 对这五种调用单独设置 `TERM=xterm`。在受影响 VPS 上重跑一键安装后，从实例页分别点“立即检测”验证。图片报告仍需 TcpQuality 报告服务可用并允许上传；网络/上传失败时查看保留的文字诊断。
- **全速双向计划一直等待或提示缺少 speedtest**：主题、插件和该 VPS 的 runner 都需要升级至上文版本；在 VPS 重新运行一键安装命令，等待实例页显示“全速双向 · 可用”。原有单机计划、限速上传结果和密钥会保留。
- **公开目标不可选**：确认插件已升级并启用，主题能读取插件目录；单机弹窗选择“路径追踪”或 iperf3 检测，再切到“公开候选”。目录暂不可用时可用“自定义主机”。
- **「Komari 节点 UUID 无效」**：36 位带连字符的值才是 UUID。实例页已自动填入安装命令。64 位十六进制值是探测器密钥，不能填进 UUID 栏。
- **「节点凭证无效」**：检查它属于当前实例 UUID；若刚重置过，请用新值重新运行向导。重置后旧值立即失效。
- **「无法同步 Komari 分组」**：确认插件 v1.3.0 或以上已启用且批准系统 RPC 权限，重试方案面板。同步失败时保留已有计划和凭证，待恢复后继续继承。
- **日志出现 `lstat .../state.json`、`Err:2`**：插件 v1.2.0/v1.2.1 首次读取尚不存在的状态文件时无法正确识别 Komari 1.4.3 的 Go 错误。升级插件到 v1.3.0 或以上后重新启用即可自动建立状态文件；无需手工创建或删除 `state.json`，已有数据不会清除。Komari 每次加载插件会清空该插件的内存日志；同样的错误出现多次通常是启动和每分钟调度再次触发，并非旧版本日志跨加载保留。
- **「等待首次连接」或「探测器离线」**：检查上面的 systemctl/journalctl、VPS 到面板的出站 HTTPS、反向代理的 `Authorization` 转发。单独调用凭证验证接口不代表 systemd 服务已在线。
- **已保存计划但没有结果**：看实例页的「等待接入 / 安装依赖 / 探测器上线」提示；计划默认错峰启动。可在就绪后立即运行，任务状态每 10 秒更新。
- **工具显示缺失**：确认依赖安装在 systemd 服务 PATH，TcpQuality 入口与 core 脚本相邻且入口可执行。重新运行一键安装命令以补装依赖并升级 runner；旧 runner 可能显示「待检测」。
